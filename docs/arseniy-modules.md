# Документы, хранение и PDF: контракт для команды

Это реализация зоны Арсения. Telegram, пользовательские сессии, предобработка
изображений и production OCR ещё не реализованы и принадлежат соседним модулям.
Интерфейсы ниже — рабочее предложение для интеграции, требуют согласования втроём.

## DocumentService — входная точка для бота

Один экземпляр соответствует одной лекции и владеет Document и FileStorage.
PDF backend передаётся по ссылке и должен жить дольше сервиса. Telegram ID,
команды, скачивание файлов и очередь задач сервису неизвестны — ими управляет Андрей.

- `addPage(source)` импортирует файл и добавляет страницу, возвращает SlideId.
- `snapshot()` возвращает копию документа; менять её можно без изменения сервиса.
- `removePage`, `movePage`, `rename` редактируют документ.
- `replacePageImage(index, source)` импортирует уже подготовленное изображение Егора,
  сохраняет ID страницы; сам обработку не выполняет.
- `generatePdf()` синхронно создаёт новый PDF внутри хранилища сервиса.
- `close()` выполняет очистку после отправки или отмены; повторный вызов допустим.

Состояния: Collecting → Generating → Collecting; Collecting → Closed.
При ошибке генерации сервис возвращается в Collecting — можно исправить данные
и повторить попытку. Закрытый сервис повторно использовать нельзя.

Во время Generating запрещены повторная генерация, изменения и close. Это защита
от повторного входа, **не синхронизация потоков**. Андрей должен сериализовать
обращения к одной лекции и не уничтожать сервис, пока работает генерация.
Разные лекции могут обрабатываться независимо только с независимыми OCR-движками
или внешней сериализацией общего backend.

Результаты повторных генераций и старые версии изображений хранятся до close.
Это сохраняет валидность снимков и позволяет закончить отправку уже созданного PDF.
После close все пути внутри сервиса недействительны. Для долгоживущих сессий
нужны будущие лимиты/TTL: сейчас автоматического ограничения объёма нет.
Отмена во время OCR не реализована: нужно дождаться окончания операции, затем close.

## Document и Slide

- Namespace: `lecture2pdf`; заголовки `document/Document.h` и `document/Slide.h`.
- `Document(title)` хранит название и последовательность страниц.
- `addPage(path)` возвращает уникальный внутри документа `SlideId`.
- Индексы в `page`, `removePage`, `movePage`, `setImagePath` начинаются с **нуля**.
- `movePage(from, to)` ставит страницу на индекс `to` в итоговом документе.
- ID сохраняется при перемещении и замене пути и не переиспользуется после удаления.
- `setImagePath` позволяет Егору передать путь к подготовленному изображению.
- Модель не читает файлы. Существование изображения проверяется перед PDF-генерацией.
- `slides()` возвращает только const-доступ. Название и пути не должны быть пустыми.
- Некорректные аргументы: `std::invalid_argument`; индексы: `std::out_of_range`.
- Ссылки на страницы не сохраняйте через операции изменения вектора.
- Document копируется: перед запуском фоновой генерации сделайте снимок.

Снимок не копирует файлы: хранилище должно жить, пока они нужны генерации и отправке.
Изменять один Document одновременно из нескольких потоков нельзя.

## FileStorage

`FileStorage(root)` создаёт собственный случайно именованный подкаталог в существующем
root (по умолчанию системный temp). Не используйте пользовательское имя лекции или
Telegram filename как путь каталога. `importFile` копирует обычный файл в хранилище,
`newPath(".pdf")` выдаёт новый путь, но не создаёт сам файл.

Хранилище не копируется и не перемещается; для сессии удобно `unique_ptr<FileStorage>`.
После `cleanup()` повторное использование запрещено. Деструктор очищает только
собственный каталог без исключений. Явный cleanup сообщает об ошибке очистки.
Для отмены сначала остановите и дождитесь обработки, затем удаляйте файлы.

На POSIX права каталога ограничиваются владельцем. На Windows применимость прав
std::filesystem ограничена; защита зависит от ACL родительского каталога. Это не
песочница против локального злоумышленника, подменяющего файлы или каталоги.
После аварийного завершения процесса временные каталоги могут остаться: очистка
устаревших сессий и лимиты хранения — отдельная задача, пока не реализованная.

## PdfGenerator и IPdfBackend

`PdfGenerator(backend)` использует backend по ссылке (он должен жить дольше генератора).
`generate(document, outputPdf)`:

1. Отклоняет пустую лекцию, отсутствующие изображения и существующий output.
2. Создаёт изолированный промежуточный каталог рядом с output.
3. Вызывает backend с документом в текущем порядке.
4. Проверяет обычный файл и сигнатуру `%PDF-` (это не полный PDF-валидатор).
5. Публикует результат через эксклюзивную жёсткую ссылку, не заменяя чужой файл.
6. Очищает промежуточные файлы, включая путь ошибки.

Родитель output должен существовать. Расширение строго `.pdf`. Для публикации
нужна файловая система с hard links (например, APFS, ext4, NTFS). На неподдерживаемой
ФС операция завершится ошибкой без небезопасного fallback. Результат не удаляется
при завершении генератора; если он внутри FileStorage, его удаляет владелец хранилища.
Деструктор очищает staging best-effort; ошибки явного файлового I/O передаются выше.

Backend обязан закрыть дескрипторы до выхода, не менять Document и не подавлять ошибки.
Системные ошибки файловой системы — `filesystem_error`, ошибки рендера — `runtime_error`.
CommandHandler должен преобразовать их в понятное сообщение, не показывая пользователю
внутренние пути. Ограничения размера и числа страниц согласуются отдельно.

## Стык с Егором: TesseractPdfBackend

Адаптер получает уже инициализированный `TessBaseAPI&` и callback
`void(const Slide&, TessBaseAPI&)`. Callback устанавливает изображение и выполняет
распознавание; при ошибке бросает исключение. PDF-адаптер добавляет готовую страницу
через `TessPDFRenderer::AddImage`, сохраняет изображение и невидимый текстовый слой.

Движок и callback должны жить весь вызов. Один TessBaseAPI нельзя одновременно
использовать в разных генерациях. Перед callback адаптер очищает данные прошлой страницы.
Изображение, использованное OCR, должно иметь геометрию итоговой страницы; наложение
OCR одной геометрии на другую не поддерживается. Цветная страница с отдельно
бинаризованным OCR-входом требует отдельного эксперимента, не обещана адаптером.

Это не навязывает Егору реализацию IOcrEngine. Callback может вызывать его модуль;
если удобнее иной контракт, меняем стык после согласования, а не дублируем OCR.
`examples/pdf_demo.cpp` содержит минимальный OCR исключительно для проверки PDF.

## Пример для Андрея

```cpp
#include "document/DocumentService.h"

// pdfBackend настраивается с OCR Егора и живёт дольше lecture.
lecture2pdf::DocumentService lecture(pdfBackend, "Лекция 1");
lecture.addPage(downloadedImagePath);
// Повторить для остальных файлов в порядке поступления.

auto output = lecture.generatePdf();
// Отправить output пользователю и ДОЖДАТЬСЯ завершения загрузки.
// Только после этого:
lecture.close();
```

Если бот использует асинхронную отправку, экземпляр lecture должен храниться
в объекте пользовательской сессии, а не в локальной переменной обработчика команды.
Для отмены новой загрузки и завершения лекции вызывается тот же close, но только
когда нет активной генерации/отправки. Пример не создаёт очередь или потоки за Андрея.

Преобразование индекса из команды пользователя: внешний номер 1 соответствует
внутреннему индексу 0. Перед вычитанием единицы проверьте, что номер положительный.

Инкапсуляция — закрытое состояние Document/Slide. Композиция — страницы документа
и передача backend в генератор. Полиморфизм — IPdfBackend, реальный адаптер и fake
в unit-тестах. RAII — владение временными файлами в FileStorage. Избыточное
